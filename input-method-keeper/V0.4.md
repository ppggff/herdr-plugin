# Input Method Keeper v0.4

Status: released as
[v0.4.0](https://github.com/ppggff/herdr-plugin/releases/tag/v0.4.0) on
2026-07-27.

Theme: **one compact control surface, no new policy system**.

  byte-for-byte, the original ABC input source was restored, the temporary

resolved backend executable was the bundled helper inside that managed root.

Version 0.4 should make occasional configuration and health checks easier
without changing the automatic pane-memory behavior delivered by v0.3. The
primary addition is a small keyboard-driven settings popup. The existing
dashboard remains the live, read-only view, and existing actions remain valid
for automation and compatibility.

## Why This Release

Version 0.3 made the core behavior quiet, fast, and self-maintaining. The
remaining usability cost is fragmented control:

- common settings are spread across 9 configuration actions;
- status and diagnostics are separate actions;
- the dashboard shows health but intentionally cannot change anything; and
- users must remember action names or edit `config.json` for occasional setup.

The current manifest exposes 12 action ids. Herdr 0.7.4 does not provide a
manifest field for hiding or deprecating individual actions, so v0.4 cannot
honestly reduce command-palette entries while preserving those ids. Instead it
establishes one recommended human-facing control surface and keeps the actions
as stable programmatic entrypoints.

## Release Preconditions

Implementation should start only after the v0.3 release has completed a normal
post-release observation period:

- automatic reconciliation remains safe and advances after it becomes due;
- focus events show no sustained correctness or latency regression;
- focus and debug log rotation behave as documented; and
- no v0.3 correctness issue requires a patch first.

These are sequencing checks, not new v0.4 features.

## Product Promises

Version 0.4 has five user-facing promises:

1. Opening and closing settings does not change pane memory, input source, or
   configuration.
2. A setting changes only after an explicit Enter action. If the shared
   mutation would delete stored pane records, remove unreadable state, or
   repair an invalid config, the popup shows the exact effects and requires
   confirmation first. Previewing a change never writes user config, state, or
   logs; it may create internal coordination lock files.
3. The popup uses the same mutation semantics as the existing actions. There
   are not two implementations of config or pane-memory policy.
4. The automatic focus handler, dashboard, action ids, config file, and state
   schema remain compatible with v0.3.
5. Settings remains small and dependency-free. It does not become a rule
   editor, log viewer, pane manager, or general plugin framework.

## Primary User Experience

### Entrypoint

Add a second plugin pane entrypoint:

```toml
[[panes]]
id = "settings"
title = "Input method keeper settings"
placement = "popup"
width = "80%"
height = 22
command = ["sh", "bin/ime-keeper", "settings"]
```

Open it with:

```sh
herdr plugin pane open \
  --plugin ppggff.input-method-keeper \
  --entrypoint settings
```

Herdr 0.7.4 already supports session-modal plugin popups. A popup does not
become a tiled pane, receive a pane id, change the underlying focused pane, or
emit pane lifecycle events. This is preferable to a normal split for settings:
the control surface does not acquire its own pane memory and disappears when
the command exits.

The plugin does not register a default keybinding. Users may bind the command
themselves if they open settings frequently.

### Layout

The first version stays within one screen and has no nested pages:

```text
Input Method Keeper                         session=default
enabled=on  action=keep  backend=helper     health=ok

Settings
> Enabled             on
  Default action      keep
  Default source      ABC       current=ITABC
  Backend             helper
  Debug logging       off

Pane memory  live=40 stored=40 unmatched=0 missing=0 reconcile=ok
Logs         focus=1.4MiB/1 debug=4.4MiB/1

Up/Down or j/k move   Enter change   r refresh   q/Esc close
Ready
```

The popup shows only the settings it can change plus the compact health summary
already available to the dashboard. The full workspace/tab/pane hierarchy
remains in the dashboard.

### Keyboard behavior

- `Up` / `Down` and `k` / `j` move between rows.
- `Enter` toggles a boolean, opens an inline choice for an enum, or performs the
  row's explicit operation.
- `Left` / `Right` changes the highlighted choice while an enum is open;
  `Enter` applies it and `Esc` cancels it.
- `r` rebuilds the read-only snapshot.
- `q` and `Esc` close the popup when no choice or confirmation is active;
  `Esc` cancels the active choice or confirmation.
- `Ctrl-C` always closes the popup safely.
- Unknown keys do nothing and do not show repeated warnings.

The interface does not poll in the background. It refreshes when opened, after
an operation, and when the user presses `r`. This keeps subprocess and Herdr
queries out of an idle settings popup; the live dashboard remains the surface
for continuous observation.

### Operation feedback

Each operation renders one short result line such as:

```text
Updated: default action is keep
Cancelled: pane memory was not cleared
Updated: backend is helper; health check failed
Changed while waiting: review the setting again
```

Errors stay visible until the next operation or refresh. A failure leaves the
popup open and restores the previous terminal mode before any uncaught exit.
Raw tracebacks are written to stderr/plugin logs rather than painted into the
interface.

## Settings and Side Effects

The popup exposes only existing configuration concepts:

| Row | Operation | Typical pane-memory effect |
| --- | --- | --- |
| Enabled | Toggle `enabled` | Existing toggle semantics request a current-session clear. |
| Default action | Choose `keep`, `reset`, or `ignore` | Existing policy semantics may request a current-session clear. |
| Default source | Store the backend's current input source | None while policy is `keep`. |
| Backend | Choose bundled helper or `macism` | None while policy is `keep`. |
| Debug logging | Toggle `debug` | None while policy is `keep`. |

Confirmation is outcome-based, not hard-coded by row. The shared mutation path
first computes the existing `clear_records` result and checks current-session
pane memory under `run.lock`. If the mutation requests a clear and at least one
record exists, the popup returns to a confirmation state without writing. This
also covers an unexpected nonempty store under `reset`, `ignore`, or disabled
mode. If state cannot be parsed reliably, it is unknown rather than empty: a
requested clear must warn that the unreadable state file and `focus.dirty` will
be removed and require confirmation. Only an idempotent clear of a successfully
read, empty store can proceed without a prompt.

For default source, show the exact current source before applying. After a
backend change, refresh and report the selected backend's health.

The popup does not expose `notify_on_focus`, `pane_status_on_focus`,
`focus_log`, `status_ttl_ms`, session naming, backend argv, or retention sizes.
Those remain advanced `config.json` fields because a complete config editor
would make the surface harder to understand than the problem it solves.

Diagnostics remain read-only in this release. `doctor` and `doctor-gc-all`
stay explicit actions/CLI commands because they can repair files, force
reconciliation, run backend checks, or delete aged session state. They should
not be placed next to harmless settings without a stronger recovery flow.

## Mutation Semantics

One neutral `mutations` module owns user-triggered config mutation, locking, and
pane-memory side effects. It accepts only the existing explicit mutation names;
it is not a generic command bus or settings framework.

Its popup-facing operation uses a bounded two-phase protocol:

1. Acquire the existing global `run.lock` in blocking mode.
2. Read config and current-session pane memory without repair or mutation, then
   briefly enter `StateStore.dirty_guard()` to snapshot `focus.dirty`.
   Capture fingerprints of the exact config, state, and dirty-marker contents,
   including missing-file sentinels. A missing config uses defaults for preview;
   an invalid config remains untouched and is marked as requiring repair.
   Missing state is empty; invalid or unreadable state is marked unknown and
   must not be treated as a zero-record store.
3. For `set-default-input-source`, read and retain the exact current source that
   will be shown to the user and written if the operation applies.
4. Compute the exact target config and existing `clear_records` result in
   memory. Do not represent `toggle-enabled` as a deferred toggle; record the
   resulting target `enabled` value.
5. If the target would clear a nonempty or unreadable store, or repair invalid
   config, release the lock and return a confirmation token containing the
   mutation name/value, exact target effect, displayed source when applicable,
   known record count or unreadable-state warning, and the config/state/dirty
   fingerprints. Write, repair, and delete no user data; acquiring coordination
   may create `run.lock` or `dirty.lock`.
6. If no confirmation is required, apply the computed target before releasing
   `run.lock`. When a clear is requested, enter `dirty_guard()`, atomically write
   config, and call `StateStore.clear_locked(guard)` before leaving the guard.
   There is no preview/apply or marker-check/unlink race.
7. When a token is confirmed, reacquire `run.lock`, then enter `dirty_guard()`.
   Compare config/state fingerprints and the guard's dirty fingerprint with the
   token while holding both locks. If any changed, release both and return
   `preview_stale` without changing user data so the popup can rebuild and ask
   again.
8. If the token is current, keep the guard through any requested state and
   dirty-marker clear. Apply the exact config target the user reviewed. For an
   invalid config, create the normal backup only at this point. Atomically write
   `config.json`, call `clear_locked(guard)` when required, then leave the guard
   and release `run.lock`.

The confirmation token is an internal, single-use capability for one explicit
mutation; it is not persisted and cannot authorize another setting. Binding it
to exact target values prevents a concurrent CLI action from reversing the
meaning of `toggle-enabled`. Retaining the displayed input source prevents a
later backend read from silently writing a different default source.

Existing CLI actions use the same application operation in noninteractive mode
and preserve their v0.3 behavior: they recompute and apply within one `run.lock`
interval, taking the dirty-marker lock only around marker access, and retain the
current writable-load/repair and clear semantics without a popup confirmation
step.

### Dirty-marker serialization

Add one session-scoped `dirty.lock` owned by `StateStore`. The store exposes an
opaque `dirty_guard()` plus an internal `clear_locked(guard)` operation.
`mark_dirty`, `clear_dirty`, and the ordinary public `clear` acquire a guard
themselves; a caller that already owns a guard must use the locked variant and
must never reacquire the file lock. Mutation preview may hold `run.lock` and
briefly enter a guard for its snapshot; confirmed apply holds them in the fixed
order `run.lock` then dirty guard through final validation and clear.

No code may acquire `run.lock` or `focus.lock` while already holding
`dirty.lock`. The losing focus-event path takes only `dirty.lock` for its short
marker write. This prevents deadlock and closes the interval between validating
and deleting the marker without making dirty writers wait for backend or Herdr
operations.

`dirty.lock` is an internal coordination file, not durable state. It is created
lazily, carries no user data, and requires no migration.

The TUI must not invoke `herdr plugin action invoke`, and neither caller keeps a
second copy of mutation, confirmation, locking, or pane-memory rules.

Backend selection changes the stored backend configuration. The next snapshot
must construct a new backend executor from the new config; a long-lived popup
must not keep using the executor created before the change.

## Read and Write Boundaries

Opening, navigation, choice preview, cancellation, refresh, and closing are
read-only. They may read config, current input source, live Herdr panes, stored
pane memory, and log health. They must not:

- create or repair `config.json` or `state.json`;
- acquire `run.lock`;
- clear pane memory;
- select an input source;
- run automatic or forced reconciliation; or
- append debug/focus logs solely because the UI refreshed.

Only an explicit Enter operation enters the mutation path. A preview or stale
confirmation cannot create, repair, rename, clear, or rewrite user config,
state, backup, or log files. Internal lock files are the only allowed
filesystem artifact of coordination.

## Module Ownership

Add one TUI feature module and one narrow application operation module rather
than a reusable framework:

```text
cli
  -> settings
      -> dashboard     existing read-only snapshot collection
      -> mutations     explicit confirmed setting operations
  -> mutations
      -> config        pure validation and mutation semantics
      -> records       record presence, dirty lock, and session clear
      -> input_source  backend current source when required
      -> _files        run.lock and file-lock primitive
  -> dashboard         unchanged live read-only renderer
  -> focus             unchanged automatic behavior
```

- `settings` owns keyboard decoding, selection/confirmation state, rendering,
  terminal mode restoration, and presentation of operation outcomes. It does
  not own config persistence or pane-memory policy.
- `mutations` owns the explicit config-operation application seam, including
  `run.lock`, read-only config/state/dirty fingerprints, confirmation-token
  validation, atomic config writes, and the existing clear side effect. Both
  CLI actions and settings call it.
- `cli` parses `settings` and existing action commands, constructs adapters,
  and delegates to the appropriate module.
- `config` continues to own allowed values and the pure
  `apply_config_mutation` function.
- `StateStore` owns the `focus.dirty` path and its session-scoped serialization;
  callers do not fingerprint or unlink the marker directly.
- `dashboard` continues to own read-only collection. Settings may consume that
  snapshot but must not change dashboard rendering or mutation rules.
- `focus` and lifecycle handlers do not import `settings` and do not know
  whether a popup is open.

Do not introduce a widget toolkit, generic screen/router abstraction, command
bus, settings schema framework, or background coordinator for this surface.

## Terminal Safety

The popup may use the Python standard library and the existing ANSI style. Any
raw-terminal implementation must:

- enter raw/cbreak mode only after the initial read-only snapshot succeeds;
- restore termios state and cursor visibility in `finally`;
- handle `SIGINT`, `SIGTERM`, EOF, and command failure without leaving the
  terminal unusable;
- disable color when `NO_COLOR` is set or `TERM=dumb`; and
- produce deterministic plain-text rendering for tests.

No new runtime dependency is added for v0.4.

## Action Surface and Compatibility

- Keep all 12 existing action ids and their behavior unchanged.
- Keep the `dashboard` pane id, split placement, CLI flags, and read-only
  behavior unchanged.
- Add only the `settings` pane entrypoint and `settings` CLI command.
- Keep plugin id, config/state locations, config shape, and state version
  unchanged.
- A lazily created internal `dirty.lock` may appear beside `focus.lock`; it has
  no persisted schema or migration requirement.
- Keep minimum Herdr version at 0.7.4 because that version supports plugin
  popup placement.
- Do not add an `open-settings` action merely to launch the pane; that would
  increase the visible action count. Documentation and optional user
  keybindings are sufficient.

README examples should recommend the settings popup for occasional human
configuration and retain the action table as the scripting and compatibility
reference. A future Herdr manifest feature for hidden or deprecated actions can
be evaluated separately; v0.4 does not depend on one.

## Delivery Order

Implement v0.4 as small observable slices:

1. Add `settings --once` plain rendering from the existing read-only dashboard
   snapshot. It performs no mutation and gives tests a deterministic seam.
2. Add the popup manifest entrypoint and a keyboard loop with navigation,
   refresh, exit, and guaranteed terminal restoration, still read-only.
3. Move current config-mutation orchestration from `cli` into a narrow neutral
   `mutations` module without changing any existing action behavior.
4. Add session-scoped dirty-marker serialization and concurrency tests without
   changing focus decisions or marker payloads.
5. Wire debug, backend, and default-source operations through the shared
   mutation path.
6. Add outcome-based confirmation tokens for every popup operation whose shared
   mutation would clear a nonempty/unreadable pane-memory store or repair
   invalid config; reject stale tokens without writing.
7. Update user documentation and run the complete validation matrix.

Each slice must preserve the v0.3 focus path and keep the settings popup usable
with a fake backend before any real input-source test.

## Release Acceptance

Version 0.4 is ready only when all of the following are true:

- All v0.3 unit, smoke-contract, fake-backend, rapid-focus, and real-backend
  checks still pass.
- Opening, refreshing, navigating, cancelling, and closing settings are proven
  read-only, including when config/state files are missing or invalid.
- Tests cover every key state, enum cancellation, unknown keys, narrow terminal
  rendering, `NO_COLOR`, `TERM=dumb`, EOF, and terminal restoration after an
  injected exception.
- Each popup mutation produces the same config and pane-memory result as its
  existing CLI action.
- No popup operation can clear a nonempty pane-memory store without
  confirmation, including unusual nonempty state under disabled, `reset`, or
  `ignore` policy.
- An invalid or unreadable state file is never treated as empty. Tests prove a
  requested clear reports the unknown state and cannot delete `state.json` or
  `focus.dirty` without confirmation.
- Preview and stale-confirmation tests prove config repair, backup creation,
  state clear, and config writes do not occur before a current token is
  accepted. Creation of internal `run.lock`/`dirty.lock` files is allowed and
  is not treated as a user-data mutation.
- Concurrent config/state/dirty-marker changes invalidate a confirmation. Tests
  cover an intervening enabled toggle, pane-memory change, and backend change. An
  intervening host input-source change cannot alter the retained default-source
  target; the applied value always matches what the accepted prompt displayed.
- A `focus.dirty` file created, replaced, or changed while confirmation is open
  invalidates the token, so an old prompt cannot delete a newer pending focus
  marker.
- Tests pause confirmed apply between its dirty fingerprint check and clear,
  then race `mark_dirty`; the writer must serialize after the clear and leave
  the new marker present. Lock-order tests prove no path takes `run.lock` or
  `focus.lock` while holding `dirty.lock`.
- Backend changes rebuild the backend executor before the next snapshot and
  surface an unavailable backend as health/error output rather than a crash.
- A popup opened on Herdr 0.7.4 does not create a pane record, change the
  underlying focused pane, or trigger a focus selection.
- Existing action ids, dashboard output/contracts, config files, state files,
  managed installs, and local links remain compatible.
- Idle settings performs no polling and adds no focus-path work.
- Release evidence records the reference Herdr/macOS versions and a manual
  pass through every setting and confirmation path.

## Non-Goals

Version 0.4 does not add:

- a rule engine, per-workspace/project/agent/cwd settings, or an ignore list;
- editing arbitrary config keys or backend argv;
- pane focusing, pane-memory editing, or reset-selected-pane behavior;
- a log viewer, log search, or live event stream;
- doctor, garbage collection, repair, or backend select self-test inside the
  popup;
- mouse interaction, fuzzy search, nested pages, themes, or a widget framework;
- a daemon, LaunchAgent, background coordinator, or continuous input-source
  observer;
- new input-method policy or changes to focus/lifecycle behavior;
- removal or hiding of existing manifest actions; or
- Linux, Windows, or a Swift rewrite of plugin policy.

Pane inspection and explicit pane-memory operations should be considered only
after the compact settings surface has real use and a concrete need. They are
not required to call v0.4 complete.
